1 · Why this work package was first

Nepal Privacy Act 2075

Data-controller duties apply to schools and ed-tech; breach notification is a legal duty. LOG treats this as a hard constraint, not a checklist (see runbook for the S1/S2/S3 procedure).

Child data is the sharpest edge

05 documented the $6.25M US biometric-data settlement and Nepal's child-data scrutiny. Guardian consent must be evidenced per learner, per registration path — never assumed.

Offline-first is a privacy surface

The sync-queue (IndexedDB) holds learner work between visits. It is now encrypted at rest — endpoint/method stay plaintext for routing, payloads do not.

3 · The erasure data map

One transaction (DeleteAccountTx in privacy_repo.go). Learner-private rows are deleted; rows that carry the school's context are anonymized so teachers keep their rosters and history without personal data. The erasure audit entry is written atomically with UserID="" and erasure_hash=sha256(userID)[:16] — the only joinable trace, containing no personal data.

5 · Sync-queue encryption at rest

Design

  • • AES-GCM-256, non-extractable CryptoKey, fresh 12-byte IV per record
  • • Key persists in sync-keys IDB store (DB version 4) — survives logout so queued work syncs after re-login
  • • Headers + body encrypted; endpoint/method/timestamp plaintext for routing
  • • SHA-256 fingerprint of method|endpoint|body for dedup
  • • No WebCrypto (non-secure context)? Honest enc:null plaintext fallback, same as legacy records
  • • Decrypt failure → record preserved, never deleted; flush stops on 401 and asks for re-login

Sneakernet escape hatch

Exported .logsync files contain decrypted plaintext records by design — the receiving device has no key. They are the user's own data; treat the file like a password. Export refuses to run if any record cannot be decrypted (no silent data loss).

7 · Decisions log (why, not just what)

Every non-obvious call in this pack was made against a concrete constraint, and recorded so a future reader can disagree with it properly.

DecisionChosenRejected because
Cipher for queue-at-restAES-GCM-256 via WebCryptoXChaCha20-Poly1305 is better suited to streaming but has no native WebCrypto binding — the fallback would have meant hand-rolling crypto, which is how queues get compromised.
Key storageNon-extractable CryptoKey in IndexedDB (sync-keys)localStorage keys are extractable by any same-origin script; an extractable key is the same as a plaintext queue. Non-extractable survives logout, which the sync contract requires.
IV strategyFresh random 12-byte IV per recordReused IVs with AES-GCM leak keystream; a per-record nonce keeps dedup honest (same payload, different ciphertext).
What stays plaintextEndpoint, method, timestamp, fingerprintRouting needs them; fingerprint is a SHA-256 hash, not content. Encrypting everything would break the sync layer's queue semantics for zero security gain.
Erasure: delete vs anonymizeLearner rows deleted; school rows anonymizedA school's class roster and announcements carry the institution's context, not the child's. Deleting them would rewrite school history; keeping them verbatim would leak the child. Empty-string anonymization is the middle that survives audit.
Erasure audit traceerasure_hash=sha256(userID)[:16], UserID=""An erasure must be provable but not joinable. A truncated hash lets an operator confirm a specific deletion happened without carrying a personal identifier in the audit log.
Legacy queue recordsNot migrated; flush as-isRewriting old records on upgrade means touching (and possibly losing) learner work. They expire naturally on flush; the window is days, not months.
Export transportContent-Disposition: attachment, Cache-Control: no-storeAn export is a moment-in-time snapshot; caching it client-side (the default for GET via fetchWithCache) would serve stale personal data. Settings page fetches it directly, bypassing the cache layer deliberately.
Consent re-grantUpsert, never duplicate; withdrawal flips statusDuplicate consent rows make "which grant is active?" ambiguous for auditors. One active row per (user, type) with a status flip is the minimal honest model.
Guardian evidencedisclosure_hash = sha256 of the exact notice text rendered; required for guardian grants (400 otherwise)An unprovable guardian grant is no evidence at all. Hashing the presented text (COPPA §312.5 practice) lets the school later prove what the guardian saw; drift between rendered text and hash invalidates the grant by construction (the JSX renders from the same constants).
Disclosure hash on plain HTTP LANsHonestly-labeled djb2-<hex> fallback, accepted by the backendSchool servers may run plain HTTP without crypto.subtle. Blocking consent there would lock every learner out; a weak-but-flagged hash keeps the gate functional and the record honest — same philosophy as the queue's enc:null fallback.
Client IPs on consentNever persisted (gorm:"-")An IP adds no evidentiary weight for District Court practice and expands the attack surface for no benefit; the audit log keeps the standard fields.
Post-erasure physical scrubPRAGMA wal_checkpoint(TRUNCATE) + VACUUM, plus _secure_delete=ON in the DSNSQLite forensics: DELETE alone leaves recoverable cells in freelist pages and the WAL. The checkpoint empties the WAL, VACUUM rebuilds the file, and secure_delete zeroes b-tree cells. Best-effort by contract — the erasure already committed; failures are logged and the runbook covers manual follow-up.
Backups around erasureOperators destroy pre-erasure backupsA VACUUM INTO/.backup snapshot taken before the erasure still contains the rows — the live DB being scrubbed does not retroactively clean copies. Runbook §5 remediation row.

9 · Open notes (honest flags)

• No POST /api/v1/auth/register route exists — registration happens via OTP + Google. Consent is therefore captured post-auth via POST /me/consent, gating both paths at the login UI. If a password-register flow is added later, it must call the consent endpoint too.

• Retention purge is not yet scheduled — the 2-year inactivity purge is documented (constants in privacy.go) but no cron exists; the runbook covers the manual procedure until a job lands.

• Nepali notice text — drafted for a native review per the tracker's AC (wp01t04).

• Consent gating is UI-level — the backend records whatever is posted; the frontend gates register/Google on the checkbox. Server-side enforcement would require an auth-flow change and is tracked in the plan's risk register.

• IT & Cybersecurity Bill 2082 — passed the House of Representatives (14 Aug 2025), pending National Assembly. Clause 61 would impose a 35-day purpose-based destruction clock. If enacted, retention moves from inactivity-based (2y) to event-based (graduation/withdrawal/request). Tracked in the tracker's risk register; revisit for policy 2026-08-v2.

10.5 · Round 2 — enforcement & transparency (2026-08-19)

Follow-up round driven by the research sweep: the pack's claims were checked against what the API actually returns, the legal annex against the Bill's current legislative state, and each fix shipped with its evidence. Policy version stays 2026-08-v1 — the notice text changed, so new grants carry a new disclosure_hash, but existing grants remain valid evidence of the text that was shown.

Rate-limit headers (RFC 6585/9110 practice)

  • • X-RateLimit-Remaining on every privacy/auth response — clients can show honest remaining-requests state
  • • Retry-After (window seconds) on 429 — the client knows when to retry instead of guessing
  • • Same headers now apply to the auth group (register/OTP/Google), which the endpoints share a limiter with

Erasure scrub is now verified, not assumed

  • • ScrubDeletedData returns a ScrubReport: freelist page count before/after, WAL frames, WAL bytes
  • • Handler logs it after each deletion (slog.Info) — operators can confirm the checkpoint+VACUUM actually reclaimed space
  • • Still best-effort by contract: the erasure itself already committed; failures are logged

No-disclosure commitment is data, not a checkbox

  • • Policy block now returns sharing.third_party_disclosure: false (in GET /me/consent and the export envelope)
  • • Consent notice (EN + NP) now states explicitly: no third-party disclosure, 2y data / 3y audit retention, export and delete available any time
  • • Rejected checkbox theater: a fake "no sharing" toggle would be a compliance prop with no backend record — the notice text + policy payload is the evidence

Offline storage protection surfaced honestly

  • • navigator.storage.persist() requested at boot — reduces eviction risk for the encrypted sync queue
  • • Settings shows a three-state card (Protected / Not granted / Checking) — never an invented value; the browser's answer is the UI
  • • Privacy-relevant because an evicted IndexedDB queue would lose queued learner work before sync

Legal annex correction

The IT & Cybersecurity Bill 2082 passed the House of Representatives on 14 Aug 2025 and now sits with the National Assembly. Clause 61's 35-day destruction clock stands; earlier "30-day" figures were from a pre-introduction draft. The Privacy Act 2075 itself is unchanged (still no statutory breach-notification duty). Runbook §8 updated to match — this is why the annex says "track for 2026-08-v2".

10.6 · Round 3 — the enforcement pass (2026-08-19)

The "max" pass on WP-0.1. Round 2 made the pack transparent; this round makes it enforced — the consent gate moves from the login UI into the API itself, retention stops being a documented promise and becomes a running job, and the browser is told to drop cached data at logout.

Server-side consent gate (the UI gate is no longer the only gate)

  • • RequireConsent middleware in middleware.go — every learner mutation route (enroll, unenroll, complete, sync/bulk, submit, password) now 403s without an active, evidenced guardian grant; staff roles are exempt
  • • The 403 carries code: "consent_required" and the offline queue honors it: records are preserved, flush stops, the learner is asked to grant consent in Settings — a gate rejection is never a terminal delete of queued work (AGENTS.md §3)
  • • Backed by HasActiveConsent on the privacy repo; withdrawal flips the same row, so a raw API client cannot mutate data after consent is withdrawn
  • • Tests: TestRequireConsentGate (no-consent 403, granted passes, withdrawn blocks, staff exempt)

Retention purge is now a running job, not a promise

  • • PurgeExpiredData: inactive learner accounts (no activity for 2 years) are erased via the full erasure map — school context survives, anonymized audit row written per erasure; audit rows past 3 years are deleted
  • • Runs at startup + daily ticker in main.go, plus manual POST /api/v1/admin/maintenance/purge (rate limited, returns the purge report as evidence)
  • • Staff are never purge candidates; FindInactiveStudentIDs checks both learner_activities.completed_at and progresses.last_activity_date
  • • Tests: TestPurgeExpiredData (stale learner erased + audit entry written, active learner + staff kept, old audit rows dropped, fresh kept)

Shared-device hygiene at logout

  • • Clear-Site-Data: "cache", "cookies", "storage" on both POST /auth/logout and POST /auth/logout-all — a school LAN shared device cannot serve cached authenticated pages or a cached /me/export bundle after the session is revoked
  • • X-RateLimit-Limit joins X-RateLimit-Remaining on every privacy/auth response (RFC 9110 draft-7 headers)

What this round deliberately did not change

  • • Policy version stays 2026-08-v1 — no notice text changed, so the disclosure_hash evidence remains valid
  • • .logsync files stay plaintext by design; the export endpoint stays uncached; IPs stay unpersisted (gorm:"-")

10 · Legal annex (what Nepal law actually says)

Research base for this pack, compiled 2026-08, refreshed 2026-08-19. Law moves — the IT & Cybersecurity Bill 2082 passed the House of Representatives in Aug 2025 and awaits National Assembly consideration.

Privacy Act 2075 (2018), in force. §12(2) consent before collecting personal/family data. Guardian/curator consent for under-18 matters, subject to the benefit-of-the-child test. §23(4) purpose disclosure — the reason the notice text exists and its hash is recorded. §26 purpose limitation. §28 correction/removal rights. §29 penalties (up to 3 years / NPR 30,000). §31 civil remedy: District Court, 3-month limitation. No dedicated regulator and no statutory breach-notification duty.

Privacy Regulation 2077. §5(2)(b) written consent required to disclose/publish electronically stored data (kept in consent_records); Rule 10 notice must state purpose, content, objective, collection time, method, assurances.

DCCS Directives 2081 — apply only to licensed data centers / cloud providers: breaches go to the National Cyber Security Centre (NCSC). A self-hosted school server is outside this, but the practice is free.

IT & Cybersecurity Bill 2082 — passed the House of Representatives 14 Aug 2025; now pending in the National Assembly. Clause 61: destroy personal data within 35 days of purpose fulfillment; a purpose-based clock that would replace the 2-year inactivity retention. Digital Rights Nepal has flagged drafting gaps. Track for 2026-08-v2.

COPPA 16 CFR §312.5 (US practice, adopted voluntarily, not Nepali law) — verifiable parental consent; separate consent for AI/advertising; the disclosure-hash practice this pack implements.
