Unify completion recording (C2)

AC: single server-side path records completions; client-side-only completion removed

What was implemented

  • • applyCompletion seam in backend/internal/repository/completion_engine.go — the one transactional path that derives status, best score, supportive observation, and next-step guidance from real attempt stats.
  • • Both CompleteActivityTx (online) and SyncBulk (offline queue) delegate to it — identical outcomes on both paths, proven by TestCompletionParityOnlineVsSync.
  • • Client-side-only completion engine deleted (frontend/src/lib/adaptiveEngine.ts); the lesson page's review gate shows success only when the backend recorded the attempt or the offline queue accepted it (recorded = res.ok || queued).

Proof

  • • backend/internal/handler/wp41_test.go — parity + foreign-shape rejection.
  • • frontend/src/app/learning/[id]/page.tsx — the recorded gate.

Refactor admin handler seam (C3)

AC: admin-only logic extracted behind a service seam; unit tests cover role checks

What was implemented

  • • AdminHandler (HTTP only) → AdminService (business rules) → AdminRepository (transactions) — the review's C3 seam, applied to dashboard, users, role changes, and activity creation.
  • • Service owns validation: role must be one of the three constants (ErrInvalidRole), last-admin demotion guard (ErrLastAdmin), not-found (ErrUserNotFound); handler maps sentinels to 400/404.
  • • CreateActivityInput DTO blocks server-managed fields (id/created_at/order); display order assigned inside the same transaction as the insert + audit write.

Proof

  • • backend/internal/service/admin_service_test.go — role checks against a fake repo (invalid roles never reach the repo; repo errors propagate).
  • • backend/internal/handler/admin_test.go — last-admin guard end to end (demote-with-remaining passes, last-admin blocked, rejected changes never audited).
wp41t03 ✓

Real foreign keys (C4)

AC: schema migration adds real FKs with cascade rules; migration tested against a copy of log.db

What was implemented

  • • backend/database/migrate_fks.go: idempotent table-rebuild migration adding ON DELETE CASCADE constraints to 20 columns across 14 child tables — learner data cannot orphan when an account is erased.
  • • Existing FKs are preserved during rebuilds (the "only the first FK survived" bug caught and fixed); orphan rows are skipped with a warning — data is never destroyed by the migration.
  • • Deliberately no FK on parent_links.parent_id (pending invites hold "" until claimed) or anonymized columns (audit_logs.user_id, announcements.author_id, assignments.created_by, classes.teacher_id).
  • • Erasure map extended: DeleteAccountTx now covers parent links, support issues, and learner notes.

Proof

  • • backend/database/migrate_fks_test.go — cascade enforcement, idempotency, anonymized columns unconstrained, orphan skip; suite green against a copy of the real dev log.db.
  • • The migration surfaced 11 ghost learner-activity rows (from earlier tests' ghost users with empty emails) — cleaned, and the unique users.email index now fails loudly instead of silently.
