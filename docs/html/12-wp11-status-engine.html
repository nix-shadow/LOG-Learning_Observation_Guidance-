Per-learner status model

AC: backend stores per-learner per-activity status (not-started / active / needs-practice / completed) and exposes it via API.

What was implemented

  • • Canonical statuses not-started / active / needs-practice / completed as domain.Status* + ResolveActivityStatus (backend/internal/domain/domain.go).
  • • Exposed via GetDashboardData / GetLearningJourneyData; default is not-started — never an invented value.

Proof

  • • domain.go status constants + resolver; learner_service.go API exposure.
wp11t02 ✓

"Needs practice" determination rules

AC: rules documented and implemented (e.g. low quiz accuracy flags an activity); phrasing stays supportive — never "failed".

What was implemented

  • • Rule in completion_repo.go: accuracy < 0.7 flags needs-practice; an improving re-attempt clears the flag.
  • • Idempotent replays keep the best score; the same rules apply in the sync write path (sync_repo.go) so offline completions cannot double-flag.
  • • Vocabulary everywhere is supportive — "Review", "Practice again", "Continue" — never "failed".

Proof

  • • ENHANCEMENT.md §1.3 FIXED note; completion_repo.go + sync_repo.go; AGENTS.md §1.
wp11t03 ✓

Status UI on dashboard + catalog

AC: catalog badges and dashboard chips render real per-learner status; empty states honest.

What was implemented

  • • Catalog badges on learning/page.tsx: completed → Review, needs-practice → Practice again, active → Continue, else Start.
  • • Dashboard journey chips (dashboard/page.tsx) render the same real per-learner statuses; empty states are honest.

Proof

  • • learning/page.tsx badges; dashboard/page.tsx journey chips; honest empty states.
